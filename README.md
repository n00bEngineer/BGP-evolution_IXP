Questo progetto implementa un sistema automatizzato per il monitoraggio della latenza di rete e l'ottimizzazione dinamica del routing BGP su router basati su BIRD. Il cuore del sistema è un ciclo composto da due componenti C compilati e gestiti da script bash: `get_ip.c` (eseguito tramite `getIp_manager.sh`) legge periodicamente l'output di `birdc show protocols all`, individua le sessioni BGP attive ("Established") e le salva/aggiorna in un database MySQL/MariaDB, rimuovendo le sessioni non più attive. Subito dopo calcola, in base ai dati di latenza già raccolti, una preferenza BGP per ogni coppia router-peer e genera automaticamente un file di filtri per BIRD (`latency_filters.conf`) che privilegia i percorsi con latenza minore. `ping_monitor.c` (avviato da `ping_manager.sh`) si occupa invece di misurare la latenza reale: recupera dal database gli IP dei router target, li pinga in massa con *fping*, calcola media e deviazione standard su più campioni e carica i risultati nel database tramite bulk load CSV per efficienza, mantenendo lo stato tra un'esecuzione e l'altra. I due script bash gestiscono compilazione automatica, verifica delle dipendenze (gcc, mysql, fping), creazione di database/tabelle e l'esecuzione ciclica sincronizzata sui secondi dell'orologio (ogni 10 secondi per i ping, ogni 60 secondi per il ciclo BGP/filtri, valori configurabili). Il file `latenza_config.conf` centralizza tutti i parametri (credenziali DB, nomi tabelle/programmi, numero di campioni ping, preferenza BGP di base, ecc.), mentre `inconsis_filter_stat.c` è un'utility separata e "una tantum" che legge `bird.conf`, estrae tutti gli indirizzi dei neighbor BGP configurati e genera un file iniziale di filtri placeholder (tutti con accept;), utile come base di partenza prima che il sistema di ottimizzazione entri a regime. 

Per usare il sistema: si configura `latenza_config.conf`, si lanciano in parallelo (tipicamente come servizi/screen separati) `getIp_manager.sh` e `ping_manager.sh`, che si autocompilano al primo avvio, creano le tabelle necessarie e restano in esecuzione continua aggiornando database e filtri BIRD. `inconsis_filter_stat.c` va invece compilato ed eseguito manualmente una volta, tipicamente in fase di setup iniziale.



English version:
This project implements an automated system for network latency monitoring and dynamic BGP routing optimization on BIRD-based routers. The core is a loop made of two compiled C programs orchestrated by bash scripts: get_ip.c (run via getIp_manager.sh) periodically parses the output of birdc show protocols all, identifies active ("Established") BGP sessions and stores/updates them in a MySQL/MariaDB database, removing sessions that are no longer active; right after, using the latency data already collected, it computes a BGP preference value for each router-peer pair and automatically generates a BIRD filter file (latency_filters.conf) that favors lower-latency paths. ping_monitor.c (started by ping_manager.sh) handles the actual latency measurement: it retrieves target router IPs from the database, mass-pings them with fping, computes average and standard deviation over several samples, and bulk-loads the results into the database via CSV for efficiency, preserving state across runs. Both bash scripts handle automatic compilation, dependency checks (gcc, mysql, fping), database/table creation, and clock-synchronized periodic execution (every 10 seconds for pings, every 60 seconds for the BGP/filter cycle, both configurable). The latenza_config.conf file centralizes all parameters (DB credentials, table/program names, ping sample count, base BGP preference, etc.), while inconsis_filter_stat.c is a separate, one-off utility that reads bird.conf, extracts all configured BGP neighbor addresses, and generates an initial placeholder filter file (all set to accept;), useful as a starting baseline before the optimization system takes over. To use the system: configure latenza_config.conf, then run getIp_manager.sh and ping_manager.sh in parallel (typically as separate services/screen sessions) — they self-compile on first run, create the required tables, and keep running continuously, updating the database and BIRD filters; inconsis_filter_stat.c instead should be compiled and run manually once, typically during initial setup.
